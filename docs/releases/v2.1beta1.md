# ClamAV Web UI v2.1beta1 — Beta release notes

> **Pre-release, not recommended for production without validation.** The source branch is independent of `main`; no merge is required or implied. Releasing the beta requires CI to pass.

## Overview

This beta integrates the current 2.1 application source and Configuration Center experience with secure upload-scanning deployment defaults. It carries forward the previously implemented fixes for [issues #13–#24](https://github.com/Kosztyk/clamv-webui/issues). The central goal is to prevent a fresh installation from failing uploaded-file scans when `clamd` cannot access the web container's private files.

## Scanning and file lifecycle

- **Fresh installs default to INSTREAM:** native uploaded-path scans default to `false`; `fallbackToInstream` defaults to `true`. INSTREAM works without shared upload directories and supports remote daemons. The original upload filename remains visible in the **Web UI** scan history, but native `clamdtop` cannot recover the original filename from INSTREAM.
- **Native filename mode (optional):** use `docker-compose.native-path.yml` and `Dockerfile.clamd-uid`, with a verified pinned ClamAV base image. Only the uploaded-file directory is mounted read-only. The daemon runs under a matching numeric UID (10001). Prove that daemon UID, actual file access, and container write paths all work before enabling native mode in Configuration Center.
- **Issue #18 cleanup retained:** clean uploads are deleted after completed scans by default, and infected uploaded files are deleted when quarantine is off (or moved if quarantine is enabled and the move succeeds). Uploads use private `0700` directory/`0600` file modes. Retention cleanup is 24 hours by default for eligible leftovers and never substitutes for successful immediate cleanup. A failed deletion may leave a file until recovery/retention; verify live behavior.
- PATH/WATCH jobs continue to need accessible scan roots. INSTREAM *upload* mode does not automatically make remote PATH/WATCH scanning possible.
- Scan jobs and detection metadata remain in the database after source file removal.

The login error page has an explicit anonymous GET permission, without opening authenticated routes or disabling CSRF. LDAP sign-in remains separate from local users and requires a mapped role.

## Install and upgrade safely

1. Back up the existing application database, `conf/`, and `data/`. Never overwrite a production Compose file with a generic example.
2. See [deployment examples](../BETA_DEPLOYMENT_EXAMPLES.md) and [production scanning](../PRODUCTION_SCANNING.md).
3. For existing installs, review saved Configuration Center scan mode and Compose environment overrides; changing source defaults does **not** overwrite saved GUI values.
4. If migrating a legacy, non-Flyway database, follow the database-specific migration procedure. Do not apply Flyway baseline flags blindly to a new or already-versioned database.
5. For NGINX TLS termination, use `SERVER_FORWARD_HEADERS_STRATEGY=native` only with the actual proxy peer IP/CIDR, and restrict backend HTTP access. **Do not copy `172.18.0.1/32` from another user's Docker network.**
6. Run clean and EICAR upload tests, verify scan job status, verify deletion, and (for optional native mode) inspect real daemon UID and mount access.

## Beta validation and known limitations

Source-only consistency checks do not substitute for Maven/CI and live Docker integration. Native filename mode remains hardware/deployment dependent. The Docker base-image digest must be set to a verified immutable `clamav/clamav@sha256:...` reference; sample placeholders cannot start a stack. Existing PATH/WATCH mounts may need deliberate migration to maintain function without violating issue #15.

This release is a **GitHub prerelease** when published, not a promotion of `main` or a guarantee that an untested production upgrade will succeed.
