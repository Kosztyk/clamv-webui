# ClamAV Web UI v2.1.0-beta2

This source candidate incorporates work for issues #13–#57. The [changelog](../../CHANGELOG.md) describes the changes and [RELEASE.md](../../RELEASE.md) describes the GitHub release process. The issue-specific notes below record changes made during successive beta2 revisions.

## Issue #53 — Java code quality CI gates

Java source and tests are formatted with Spotless. CI checks the changed files, enforces an 82% JaCoCo line coverage minimum and checks for decreases against the immutable comparison commit. Maven Enforcer validates prerequisites and dependency convergence. The JDK 21 and 25 matrix and the SpotBugs, FindSecBugs and PMD checks feed the always-reporting `gate`. See [Java quality gates](../ISSUE53_JAVA_QUALITY_GATES.md).

## Issue #25 fixes

- Audit fields are bounded to existing DB `audit_events` column lengths (64 for username/action/outcome/job_id/ip, 1024 for details, 32 for transport, and 255 for User-Agent). No schema changes or Flyway migrations required.
- A 10 KiB User-Agent no longer produces an overlong database insert. User-controlled details such as endpoint names and watcher paths are likewise bounded before persistence.
- `AuditService.record`, `recordScan`, and `recordResult` now call a dedicated `AuditEventWriter` using an isolated `REQUIRES_NEW` transaction and `saveAndFlush`. A failing audit insert or transaction commit is caught by the audit facade; already-completed user operations and queued scan jobs are not misreported as failed because of optional audit persistence.
- Only the action and exception **type** are logged on audit write failure; raw user-supplied details and User-Agent are not logged.
- Unit tests cover all limits, UTF-16 surrogate truncation, scan and worker events, transaction boundary, and simulated audit failures. A Spring MockMvc end-to-end test submits an authenticated endpoint creation request carrying a 10 KiB User-Agent, then checks the persisted audit row.

## Post-audit scan-worker lifecycle correction (local source candidate)

- On Spring shutdown, `ScanExecutionService` stops new dispatches and cancels only waiting in-memory tasks; their committed `QUEUED` rows remain recoverable.
- Active workers have 20 seconds to finish, then an interruption is requested and up to 5 further seconds are allowed. A forced cancellation is **not** reported as an ordinary scan `ERROR`.
- `ScanJobService` requeues interrupted `RUNNING` rows on the next single-instance startup; queued IDs are picked up in bounded batches. Automatic retries can repeat a scan, so this remains an at-least-once guarantee.
- New JUnit concurrency tests exercise graceful completion, backlog preservation, forced cancellation, and startup retry. The default Docker Compose 60-second stop window remains unchanged. See [scan queue and lifecycle details](../QUEUE_COVERAGE_UPGRADE_HARDENING.md).

## Post-audit native upload fallback correction (local source candidate)

- Native ClamD `MULTISCAN` now returns a scan verdict **without** persisting or quarantining it.
- With path scanning enabled, **only `IOException` from the native path operation** is eligible for optional INSTREAM fallback, including ClamD socket errors, command timeouts and malformed protocol responses. Unexpected runtime failures are propagated to the outer job error handler and do not cause a second scan.
- The selected scan verdict is finalized exactly once outside the fallback catch: DB writes, quarantine and notifications cannot cause an INSTREAM retry after a successful native scan.
- If native scanning fails with fallback disabled, the existing `ERROR` verdict, diagnostic and notification behavior remains unchanged.
- No new settings, DB migration or change to the previously fixed scan-worker shutdown lifecycle. Regression tests exercise native success, native I/O fallback, no-fallback failure, persistence/quarantine errors and notification failures.
- Maven/JUnit and live ClamD Docker tests remain required before production.

## Post-audit source quarantine authorization and transaction boundary corrections (local source candidate)

- For PATH and WATCH jobs, `ScanExecutionService` passes the originally authorized scan target to `QuarantineService.attemptSource` for each daemon-reported detection. Before any move, the quarantine service checks both the current allowed-root policy and exact target scope, including the target's original file/directory type. Files outside the scanned file/tree, aliases, relative/traversal paths and symlink escapes cannot be moved because of untrusted ClamD result keys.
- Rejected quarantine attempts retain the `VIRUS_FOUND` verdict and original detection signatures, annotate the job with `SOURCE_FAILURE`, and leave the unauthorized source in place. Valid detected files within a directory scan remain eligible for quarantine. Upload quarantine behavior is unchanged.
- `finishOk`, `finishFound`, `finishError` and `setQuarantinePath` now delegate to a separate `@Transactional` Spring bean, `ScanJobFinalizationService`, eliminating ineffective self-invoked transaction annotations. Short metadata transactions do not wrap daemon I/O or filesystem moves; completion metrics and audit events are published after commit, and are suppressed on rollback.
- New source-quarantine adversarial tests and a Spring transaction-proxy test are provided. An independent JDK 21 filesystem harness executed against actual `QuarantineService` and `PathPolicy` passed nine cases. Maven/JUnit and live ClamAV are not verified by the packaging environment.
- No Flyway migration, UI setting, Docker Compose change or new environment variable is required.

## Post-audit cumulative corrections — 14 November 2026

The second cross-feature audit repaired ten additional interacting findings:

- Combined directory-scan and quarantine warnings now retain the `QUARANTINE_FAILED` API status.
- Watcher fingerprint ownership includes the ClamAV endpoint ID. Overlapping roots or endpoint changes no longer borrow a stale fingerprint from another endpoint.
- **Flyway V9** (H2, PostgreSQL, MySQL, MariaDB) adds endpoint-scoped marker uniqueness and the `quarantine_artifacts` source-move journal. Legacy unowned markers are ignored and lazily pruned. Expect a **one-time full watcher rescan after upgrading**; plan capacity for that replay and back up the database first. No existing scan jobs or endpoint definitions are deleted by V9.
- Each source quarantine move has a committed PREPARED journal row before its filesystem change, then records MOVED / FAILED / HARDEN_FAILED. Startup reconciles destinations **before** resetting interrupted jobs, including cases where the final job transaction failed after a successful move. The scan's full positive verdict is staged before quarantine; successful infected detections are not reclassified as scan errors due to downstream failures.
- The first successful source quarantine destination is retained on the job; all source artifacts (original and stored location, result, signatures, timestamps) are linked through the journal. The public API remains path-redacting; do not expose the journal table to unauthenticated clients.
- Legacy CI structure checks now follow the refactored source-quarantine and transaction/audit locations; a new cross-feature test runs in both CI and the release gate.
- Independent per-root rescan deadlines avoid small-directory starvation while a different root is still traversing a very large tree.
- Unexpected upload-quarantine exceptions preserve a confirmed `VIRUS_FOUND` verdict. Restart reconciliation also covers interrupted staged positive uploads.
- Worker shutdown waits are capped at 40 seconds combined and must be at least five seconds below `spring.lifecycle.timeout-per-shutdown-phase`, which now defaults to 45 seconds. The supplied Docker Compose timeout remains 60 seconds. Coordinate custom upstream process-manager timeouts with these limits.
- Filtered-directory positive-result aggregation is bounded to 1,024 reported file paths and 16 signatures per path; truncation produces a partial-scan warning instead of silently reporting a complete scan.
- The worker claim and shutdown-state transition are serialized to avoid claiming a newly dequeued job after shutdown starts.

**Upgrade warning:** This release candidate adds Flyway **V9**, unlike the earlier post-audit beta2 archives. Back up the database, `data/` and `conf/` before running it. Never downgrade the application against a database already migrated to V9 without a supported restore/migration path. **Do not publish as production until `mvn -B -ntp clean verify`, Testcontainers migrations on all supported databases, real ClamAV scanning, and Docker SIGTERM/restart tests pass.**

## Additional cumulative quarantine/recovery corrections (V10 candidate)

- An interrupted positive directory scan is reconciled against **every** staged detection before being finalized; missing entries are retried or recorded as quarantine failures. Existing journal rows are resolved before replaying queued scans.
- An unresolved move/journal database commit does not permit the worker to mark the scan complete; successful filesystem moves remain recoverable via their deterministic journal destinations.
- Upload and source quarantines use journaled move destinations. Finished jobs with `PREPARED`/`HARDEN_FAILED` artifacts are revisited for permission hardening, and the history retention check respects every recorded quarantine artifact.

- Database schema V10 adds nullable `scan_target_was_directory` to `scan_jobs` for safe post-crash source path authorization. NULL legacy values fail closed. Fresh and upgrade migrations need validation on H2, PostgreSQL, MySQL and MariaDB.

## Quarantine evidence and mixed-warning correction (V11, local candidate)

- Source-file quarantine now journals the entire known detection set in one committed batch before moving any file; rejected paths are explicitly recorded as failures. Startup permission repair can no longer clear a quarantine warning that belongs to a different detected file.
- A source file is SHA-256/size fingerprinted before journal reservation; ordinary moves and crash recovery validate that evidence against the current source or previously moved destination. Replaced files are left untouched with an explicit quarantine warning, rather than quarantined on stale pathname evidence. Missing or legacy identity evidence fails closed.
- Upload quarantine also validates its stored bytes against the upload hash where available, and the staged job records whether quarantine was enabled when the scan completed.
- **Flyway V11** adds nullable content-evidence, failure-code and quarantine-intent fields for H2/PostgreSQL/MySQL/MariaDB. Back up databases and private volumes before upgrading; test the migrations on all four engines.
- See [V11 quarantine identity/recovery notes](../QUARANTINE_IDENTITY_V11.md). Maven/JUnit, real migrations and Docker/ClamAV crash-injection remain required before production.

## Watcher retry and live recovery candidate (V12)

- WATCH job fingerprints are owned by the committed job ID. An `ERROR` verdict schedules a durable retry with bounded exponential backoff; older jobs cannot mark newer fingerprints retryable.
- Periodic reconciliation recovers positive staged jobs and unowned, stale RUNNING jobs in bounded batches. A local active scan is never reclaimed by the periodic reconciler.
- Remote directory scans use local allowed-root/symlink preflight even when the selected endpoint differs from the primary. A disabled primary daemon-discovery observer no longer causes the remote preflight to fail.
- Truncated positive scan reports expose an `INCOMPLETE` quarantine status and `DETECTION_REPORT_TRUNCATED` error in API v1. A truncated report is **not** a guarantee of complete quarantine.
- Flyway V12 extends `processed_files` with retry ownership and deadline fields for H2, PostgreSQL, MySQL and MariaDB. See [V12 candidate notes](../WATCHER_RETRY_LIVE_RECOVERY_V12.md). Back up before migration and validate with the real Maven/JUnit, JPA, Flyway and Docker/ClamAV test suites.
