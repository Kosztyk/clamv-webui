# Issue #51 — GHCR multi-architecture, scanned and signed release images

ClamAV Web UI uses `pom.xml` as the version source. The protected `gate` check
(issue #48), tag validation, full release gate, database matrix and `clamctl`
release builds (issues #49/#50) **must all succeed** before a release workflow
may obtain registry write credentials. The separate `release` environment and
`RELEASE_PUBLICATION_ENABLED` still control making a GitHub *draft release*
public. **GHCR image publication happens earlier**, only after the checks
below; GitHub Packages visibility is configured separately.

## Container release lifecycle

1. `release.yml` runs only for tags `vMAJOR.MINOR.PATCH[-prerelease]` and
   accepts manual `workflow_dispatch` **only as a dry-run**. It verifies the
   exact git tag against POM, main ancestry and the most recent successful
   `main`-push `gate`. It rechecks the remote tag before any registry write.
2. The normal Maven/Java, browser, Testcontainers (PostgreSQL, MySQL,
   MariaDB), Docker/EICAR, Trivy CRITICAL, and six-platform Go checks run.
3. The `image-publish` job (the only job with `packages: write` and
   `id-token: write`) uses SHA-pinned QEMU/Buildx/login/build-push actions.
   It publishes an **intermediate staging tag** with two native platforms,
   `linux/amd64` and `linux/arm64`, plus BuildKit SPDX SBOM and
   `provenance: mode=max` SLSA provenance attestations. Java and scanner base
   images in the Dockerfiles are pinned by digest.
4. The pushed **index digest**, not a locally built tag, is inspected. Its OCI
   manifests must contain BOTH platforms and attestation manifests. Trivy
   v0.70.0 scans the **pushed digest twice** (one scan per architecture),
   failing on *fixable* `HIGH`/`CRITICAL` OS and library CVEs. An unavailable
   scanner, registry or vulnerability database fails the release.
5. Trivy exports a CycloneDX JSON SBOM for each architecture. `cosign sign`
   creates a keyless OIDC signature over the **pushed immutable index digest**;
   `cosign attest --type cyclonedx` attaches the SBOMs. `cosign verify` and
   `cosign verify-attestation` check certificate identity and issuer.
6. CI performs an explicit `docker pull --platform linux/amd64` of the
   **pushed digest**. It selects that exact reference through
   `CLAMAV_WEBUI_IMAGE_REF` in the existing Compose file; `docker compose up
   --no-build --pull never` cannot silently rebuild or pull an unrelated tag.
   CI checks the running container's original image reference, then invokes
   the **existing** `scripts/smoke-non-root.sh` and `scripts/smoke-eicar.sh`.
7. **Only after the smoke tests pass**, the workflow applies release aliases
   to the same OCI index and confirms each alias resolves to the exact digest.
   Beta/pre-release tags use **only their exact version**; stable releases
   use `X.Y.Z`, `X.Y`, and `latest`. A failed job cannot reach the draft stage.
8. The image digest/aliases, both CycloneDX SBOMs, and OCI manifest become
   checksummed GitHub release assets alongside the JAR, six CLI files and
   full tracked-source archive. Draft creation and protected publication
   repeat digest signature checks. `SHA256SUMS` covers **all 12 assets**.

Note: BuildKit's provenance and SPDX SBOM are native OCI attestations, while
additional CycloneDX SBOM attestations are signed through Sigstore. Image
provenance is generated by the BuildKit build, not fabricated by a release
metadata script. The image evidence JSON records the digest, tag, and policy;
its claims are independently validated by the CI steps.

## Deploy with Docker Compose

Use the [published-image Compose example](../docker-compose.ghcr.yml), which
runs the Web UI against an existing reachable clamd daemon. **The example does
not package a second clamd process in the Web UI.**

```bash
export CLAMAV_WEBUI_RELEASE_VERSION=2.1.0-beta2  # change to the release you approved
export CLAMAV_HOST=192.0.2.73                   # example: set your actual clamd host
# First verify the release's version, signature and SHA256SUMS before deployment.
docker compose -f docker-compose.ghcr.yml pull
docker compose -f docker-compose.ghcr.yml up -d --no-build
```

For a **digest-pinned** deployment using the existing Compose file, set:

```bash
export CLAMAV_WEBUI_IMAGE_REF='ghcr.io/kosztyk/clamav-web-client@sha256:<actual_digest_from_image-reference.json>'
docker pull "$CLAMAV_WEBUI_IMAGE_REF"
docker compose up -d --no-build --pull never
```

Replace the `<actual_digest...>` placeholder with the release's 64-hex SHA.
`CLAMAV_WEBUI_IMAGE_REF` is optional; without it, the source Compose file still
builds and runs `clamav-web-client:local`, as before. The `clamav/clamav:1.4.6`
scanner digest in the source Compose is currently documented as **amd64-only**;
validate companion scanner images separately for other architectures. This
is not a limitation of the **multi-arch Web UI** image itself.

## Verify the published image signature manually

For a public package, unauthenticated `docker pull` should succeed. GitHub
Packages may initially create a **private** package; in that case the owner
must set GHCR package visibility to public in GitHub's package settings, or
call `docker login ghcr.io` for authorized pulls. Use the actual published
digest in the commands:

```bash
IMAGE='ghcr.io/kosztyk/clamav-web-client@sha256:<actual_64_hex_digest>'
TAG='v2.1.0-beta2'
COSIGN_IDENTITY="https://github.com/Kosztyk/clamv-webui/.github/workflows/release.yml@refs/tags/$TAG"
cosign verify \
  --certificate-identity "$COSIGN_IDENTITY" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  "$IMAGE"
cosign verify-attestation --type cyclonedx \
  --certificate-identity "$COSIGN_IDENTITY" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  "$IMAGE"
```

For stable `v2.1.0`, the expected tags are `2.1.0`, `2.1`, `latest`.
For `v2.1.0-beta2`, the only release alias is `2.1.0-beta2`.

The GitHub release stays a *draft* until protected-environment approval;
**creating GHCR tags does not redeploy production**. The previous Docker Hub
image `kosztyk/clamav-web-client:v2` is not modified by this workflow.

## Source checks and runtime requirements

```bash
python3 scripts/check-issue51-container-release.py
python3 scripts/test-issue51-image-release.py
python3 scripts/test-issue51-policy.py
bash scripts/release-gate.sh --static-only
```

These are offline policy/unit checks, **not proof** of publication. The live
acceptance criteria require a complete GitHub Actions tag run on `main`,
GitHub Packages permission, working Trivy databases, OIDC/Sigstore and
Buildx/QEMU, plus an active clamd scanner. Do not close issue #51 until an
actual tag pull, cosign verification and published-digest smoke test succeed.
