# v2.0.0 — LDAP TLS trust and Authentication Save diagnostics

This is a maintenance update of Phase 3.1, not a schema migration or a change to authentication policy.

## LDAPS handshake failure

OpenLDAP log entry `ssl/tls alert certificate unknown` from the ClamAV application indicates a TLS certificate verification failure before LDAP bind. Keep TLS validation enabled.

On the LDAP host (192.168.68.112 in the test deployment), the original OpenLDAP test bundle contains `trust-clamav.sh` and `certs/server/ca.crt` (generated by `setup.sh`). From its directory:

```bash
cd /root/clamav-ldap-test
sudo ./trust-clamav.sh /root/clamav
```

If ClamAV Compose is stored elsewhere, supply that directory instead of `/root/clamav`.

Add to the existing **ClamAV Web UI** Compose service environment (do not overwrite other values):

```yaml
JAVA_TOOL_OPTIONS: "-Djavax.net.ssl.trustStore=/app/conf/ldap-test-truststore -Djavax.net.ssl.trustStorePassword=changeit"
SERVER_FORWARD_HEADERS_STRATEGY: "framework"
SERVER_SERVLET_SESSION_COOKIE_SECURE: "true"
```

Recreate the UI container from its Compose directory, not the LDAP or NGINX directory:

```bash
cd /root/clamav
docker compose up -d --no-deps --force-recreate clamav-web-client
```

Verify settings without disclosing credentials:

```bash
docker exec clamav-web-client sh -lc 'echo "$JAVA_TOOL_OPTIONS"; ls -l /app/conf/ldap-test-truststore'
docker exec clamav-web-client keytool -list -keystore /app/conf/ldap-test-truststore -storepass changeit -alias clamav-test-ldap-ca
```

The truststore is separate from the NGINX browser-facing certificate. Import the **LDAP test CA** (`certs/server/ca.crt`), not the NGINX CA. If the LDAP certificate has been regenerated, update the matching truststore certificate before restarting ClamAV.

The LDAP URL in this lab is `ldaps://192.168.68.112:1636`; the server certificate must contain the IP as a Subject Alternative Name.

## Why Save can say "Unexpected server response"

Old JavaScript expected only `{ok, message}` from the authentication settings controller. If Spring Security rejected the request with HTTP 403 (CSRF/session), or Spring returned HTTP 500 after an infrastructure error, the generic JSON error payload did not have `ok`, resulting in the unhelpful message.

The updated browser code shows the HTTP status, including specific advice for 401, 403, and 5xx, while preserving the entered draft. The controller also maps known TLS, bind, database, and encryption-key issues to safe explanations. It does **not** echo secrets or raw LDAP exception bodies.

To diagnose a Save failure, note its HTTP status and inspect:

```bash
docker logs --tail=150 clamav-web-client
ls -ld /root/clamav/conf
```

If a new secret cannot be encrypted because `/app/conf/auth-settings.key` cannot be created, ensure the mounted `conf` directory is writable by the ClamAV container's Java user. Preserve and back up the encryption key; deleting or regenerating it makes previously encrypted credentials unreadable.

**Testing does not save configuration.** After a successful Test, press Save with **Enable LDAP login** selected. If LDAP is enabled, Save also validates connection/TLS before activating it. Do not disable TLS verification or turn off CSRF for convenience.

Maven integration tests and a live containerized LDAP login must still be run on the Docker-enabled host. The code includes isolated diagnostic unit tests.
