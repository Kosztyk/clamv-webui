# CVE-2026-107891 — Alpine 3.24 musl VEX handling

## Decision

The runtime remains on Alpine 3.24 `musl 1.2.6-r3`. Alpine's security tracker
marks that branch/package revision fixed for CVE-2026-107891, while Docker
Scout can report `1.2.6-r6` as the fixed revision by comparing against a
different Alpine package branch. The release therefore records the branch
backport as a narrowly scoped OpenVEX `not_affected` assessment rather than
installing edge libc packages into the stable Alpine 3.24 runtime.

Evidence:

- Alpine security tracker: https://security.alpinelinux.org/vuln/CVE-2026-107891
- Docker VEX guide: https://docs.docker.com/scout/how-tos/create-exceptions-vex/
- Docker Scout VEX tutorial: https://docs.docker.com/learn/content/document-vulnerabilities-that-dont-affect-your-app/

## Release implementation

`scripts/vex_release.py` generates the document after the pushed image digest is
known. It fails closed unless all of the following remain true:

- vulnerability: `CVE-2026-107891`
- status: `not_affected`
- justification: `inline_mitigations_already_exist`
- subcomponents (matching Docker Scout 1.29+ Alpine package identities):
  - `pkg:apk/alpine/musl@1.2.6-r3?arch=x86_64&os_name=alpine&os_version=3.24`
  - `pkg:apk/alpine/musl@1.2.6-r3?arch=aarch64&os_name=alpine&os_version=3.24`
- product: the exact image digest as a Docker PURL
- advisory: Alpine's CVE-2026-107891 tracker entry

Docker Scout requires the image digest as the `pkg:docker` version for an image
whose SBOM comes from an attestation. A tag-only product can load successfully
without matching the image, leaving the finding visible, so the generator never
uses the release tag as the VEX product version.

`.github/workflows/release.yml` then attaches the validated document through the
existing GHCR staging tag with the SHA-pinned `docker/scout-action`, explicitly
using OCI referrers and the `kosztyk` Scout organization. The OpenVEX product
itself remains bound to the exact immutable digest and uses predicate type
`https://openvex.dev/ns/v0.2.0`. A second Scout step verifies that the publisher
author `https://github.com/Kosztyk/clamv-webui` is explicitly trusted and that
`not_affected` findings are filtered before the release proceeds. The release
artifact inventory also includes `CVE-2026-107891.vex.json`, and
`scripts/release-assets.py` revalidates its image digest and package scope when
assembling and approving a release.

## Docker Hub

The project's verified release workflow intentionally publishes GHCR, not
Docker Hub. VEX attestations are bound to the image in the target registry and
do not automatically appear on a separately published Docker Hub repository.
After pushing the corresponding Docker Hub image, authenticate to Docker Hub
and Docker Scout and run:

```bash
bash scripts/attach-release-vex.sh \
  docker.io/kosztyk/clamav-web-client:2.1.0 \
  2.1.0
```

The helper resolves the current immutable digest first, refuses unexpected
repositories, generates a fresh digest-scoped VEX document, validates it, and
then attaches through Docker Scout's normal attestation backend with
`docker scout attestation add --org kosztyk`. For Docker Hub the helper normalizes
`docker.io/kosztyk/...` to the short `kosztyk/...` reference before attaching; this
avoids the older full-reference `:latest` resolution problem while keeping the VEX
discoverable by `docker scout cves` and `docker scout attestation list`. It does not
push or modify image layers.

Docker Scout intentionally trusts only Docker-authored VEX by default
(`--vex-author` defaults to `<.*@docker.com>`). A plain third-party scan can
therefore show this publisher-authored VEX in the output while still counting
the CVE. To apply the assessment, explicitly trust this repository's VEX author
and filter `not_affected` statements:

```bash
docker scout attest list \
  registry://docker.io/kosztyk/clamav-web-client:2.1.0

docker scout cves \
  --org kosztyk \
  --vex-author 'https://github.com/Kosztyk/clamv-webui' \
  --only-vex-affected \
  registry://docker.io/kosztyk/clamav-web-client:2.1.0
```

With that publisher trust decision, the scan should report that VEX statements
were obtained from an attestation and CVE-2026-107891 should be filtered from
the High count. This trust requirement is a Docker Scout safety feature; the
project must not spoof a Docker-owned author merely to change default output.
If the image digest changes, generate and attach a new statement; do not reuse
the old document.

## Reassessment triggers

Reassess and regenerate the VEX statement whenever any of these changes:

- Alpine branch or base image
- installed musl version
- image digest
- Alpine's CVE disposition
- Docker Scout's advisory mapping or VEX matching behavior

The VEX is an auditable exception for a distribution backport, not a blanket
waiver for future images.
